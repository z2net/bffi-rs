# Привязка GUI и событийных библиотек из Bun

[English](https://github.com/z2net/bffi-rs/blob/main/docs/BINDING-GUI.md) | **[Русский](https://github.com/z2net/bffi-rs/blob/main/docs/i18n/ru/BINDING-GUI.md)** | [简体中文](https://github.com/z2net/bffi-rs/blob/main/docs/i18n/zh-CN/BINDING-GUI.md)

bffi - слой привязок (аналог napi-rs для экосистемы Bun): нативная библиотека на Rust компилируется в cdylib, Bun загружает её через типизированный загрузчик и вызывает. Это руководство разбирает тот единственный сценарий, который обычному napi-rs даётся плохо: **GUI / событийные библиотеки** (wry, winit, tao, SDL, ...), чьи обработчики выполняются в потоках ОС и требуют синхронного обмена с JavaScript.

Рабочий эталонный пример - [`wry`](https://github.com/z2net/bffi-examples/tree/main/wry) (полноценное окно webview, управляемое из Bun). Читайте его вместе с этим руководством.

## Модель потоков

GUI-библиотека владеет событийным циклом уровня ОС, и этому циклу нужен выделенный поток. Схема:

```text
Bun main thread (JS)                native loop thread (cdylib)
----------------------              ---------------------------
api.webview_open(cfg)  --proxy-->   EventLoop + Window + WebView
api.webview_eval(h, js) --proxy-->   evaluate_script
      |                                    |
      | pump the bffi event loop           | ipc_handler fires
      |<-- marshalled callback job ------- invoke_wait(js_cb, ...)
      |      (runs on THIS thread)         | (parked until reply)
      | resolve via webview_eval ---->     | wakes with the reply
```

- cdylib порождает поток цикла при первом вызове (`std::thread` + командный канал `EventLoopProxy`). JavaScript никогда не блокируется на окне: каждая нативная точка входа отправляет команду через прокси и немедленно возвращается.
- **JS-поток остаётся свободным для опустошения** событийного цикла bffi (`pumpUntil` / сгенерированный `loop_pump`, явный pump-контракт в `docs/DESIGN.md`). Доставки выполняются на JS-потоке, пока он опустошает цикл, - фреймворк никогда не устанавливает скрытых таймеров.
- Межпоточная легальность: на Windows цикл winit/tao спокойно живёт вне главного потока (`with_any_thread(true)`). Тулкиты Linux (webkit2gtk/gtk-init) строже в своих предположениях - там либо оградите платформу проверкой, либо опустошайте цикл на главном потоке.

## Вызов JavaScript из нативного потока: invoke_wait

Всё это держится на одном примитиве:

```rust
use bffi::{invoke_wait, Value};
use std::time::Duration;

// Runs on the GUI loop thread: calls the JS-bound callback,
// parks until the JS side answers (it pumps), returns the value.
let reply = invoke_wait(ipc_handle, &[Value::Str(body)],
                        Duration::from_secs(30))?;
```

- `invoke_wait` работает с ОБОИМИ таблицами колбэков: замыкания, зарегистрированные на нативной стороне (`bffi::register`, путь через `Value`), и JS-bound колбэки (`bffi_callback_bind` - дескриптор, который JavaScript получает, привязывая свою функцию).
- Вызов ставится в очередь событийного цикла bffi; вызывающий поток паркуется на слоте; когда JS-поток опустошает цикл, задача выполняется на нём (JSCallback привязан к потоку - это единственный легальный путь), а результат возвращается через тот же слот.
- **Таймаут обязателен.** Цикл, который никто не опустошает, не должен подвешивать нативный поток: ожидание ограничено, возвращается `ErrorCode::Timeout` (15), а опоздавший результат безвредно оседает в брошенном слоте.
- **Контракт по дедлокам** (описан в разделе 9.1 `crates/bffi/CALLING-CONVENTION.md`): JS-поток обязан опустошать цикл; никогда не вызывайте `invoke_wait` из кода, который сам выполняется внутри колбэка при опустошении на JS-потоке (повторный вход) - такой вызов по построению завершится таймаутом.
- Матрица C-вызовов для JS-bound диспетчеризации: до 2 параметров из `i32 | i64 | u64 | f64 | bool | cstring`, возвраты из `i32 | i64 | u64 | f64 | bool | cstring | void` (cstring-возврат копируется немедленно; указатель живёт только в рамках вызова). Бинарные нагрузки и композиты (массивы, records) сырой C-вызов пересечь не могут - они едут по буферизованным каналам; неподдерживаемые формы падают быстро (`UnsupportedSignature`), без блокировки.

## Конфиг-структуры: поля `Option` в records

Конструкторы GUI принимают разреженные конфигурации. Структуры с `#[derive(BffiRecord)]` допускают поля `Option<T>` по всей матрице полей - `None` пересекает границу как байт `TAG_UNIT` wire-формата, `Some(v)` - как обычное значение; TypeScript отрисовывает такое поле как `T | null`:

```rust
#[derive(bffi::BffiRecord)]
pub struct WebviewConfig {
    pub url: Option<String>,
    pub html: Option<String>,
    pub title: Option<String>,
    pub width: Option<u32>,
    pub devtools: Option<bool>,
}
```

Вложенная `Option<Option<T>>` отвергается на этапе компиляции (E010).

## Полный цикл IPC

Полный круг UI -> нативный код -> JS -> нативный код -> UI (см. [`wry/src/lib.rs`](https://github.com/z2net/bffi-examples/blob/main/wry/src/lib.rs)):

1. JavaScript привязывает свой обработчик (`bffi_callback_bind`, сигнатура `unit(str)`) и передаёт дескриптор нативному экспорту (`webview_bind_ipc`).
2. Страница отправляет сообщение (`window.ipc.postMessage`); `ipc_handler` библиотеки выполняется на потоке цикла и вызывает `invoke_wait(ipc_handle, &[Value::Str(body)], 30s)`.
3. JS-поток опустошает цикл, привязанный обработчик выполняется, его ответ доставляется обратно через `webview_eval` (разрешением промиса на странице, например `window.__bffiResolve(id, json)`).
4. Поток цикла просыпается с результатом и возвращается.

Держите обработчик быстрым и никогда не вкладывайте циклы обмена друг в друга (один активный вызов на страницу сохраняет протокол предельно простым).

## Удержание колбэков и завершение работы

- **Колбэки живут на JS-стороне**: привязанный JSCallback и его дескриптор должны жить столько, сколько нативная сторона способна их вызывать (держите объекты в реестре на уровне модуля; при завершении работы отзывайте их явно). Нативная сторона перепроверяет дескрипторы в момент диспетчеризации - отозванный дескриптор проявляется как `InvalidHandle`, а не как падение.
- **Протокол завершения**: удаление последнего окна завершает поток цикла (`EventLoop::exit`); опубликуйте закреплённый флаг завершения и позвольте JavaScript за ним наблюдать (`webview_poll_exit` в примере). При выходе Bun срабатывают зарегистрированные `Drop`-гарды на потоке цикла - не полагайтесь на atexit для потоков, которые вы породили сами.

## Заметки по упаковке

- **Windows**: загрузчик WebView2 (`WebView2Loader.dll`) должен находиться рядом с бинарником хоста - поставляйте его с платформенным пакетом; сам *рантайм* WebView2 - компонент ОС (`bffi doctor` умеет его обнаруживать).
- **Linux**: webkit2gtk и его GTK-зависимости динамические (для сборки установите `libwebkit2gtk-4.1-dev` / `libgtk-3-dev`); headless-CI для тестов с настоящими окнами нужен `xvfb`.
- **macOS**: WKWebView - часть ОС; окна для AppKit обязаны создаваться на главном потоке - паттерн работы вне главного потока из этого руководства сегодня специфичен для Windows.
- Бинарники - обычные cdylib: тот же конвейер `bffi pack` / платформенных пакетов применяется без изменений.

## Чек-лист новой привязки

1. Закрепите версии библиотек (`=x.y.z`) - GUI-крейты быстро меняются.
2. Структура конфигурации с полями `Option`; сеттеры-билдеры там, где record не выражает нужное.
3. Поток цикла + прокси-командный канал; каждый экспорт возвращается немедленно.
4. JS-bound колбэки для каждого обработчика библиотеки; `invoke_wait` с ограниченным таймаутом; экспорты в духе `evaluate` для натив -> UI.
5. Закреплённый флаг выхода + экспорт-опрос; явный экспорт `close`.
6. Rust-тесты без окон; e2e с настоящими окнами за env-гейтом (`BFFI_WRY_E2E=1` в примере).
7. README со схемой потоков и командой запуска.
