## 1. Назначение

`bffi-rs` - фреймворк нативных привязок **только для Bun** - аналог `napi-rs` для рантайма Bun.

Нативный модуль пишется на Rust, компилируется в `cdylib` и потребляется из TypeScript через `bun:ffi` и тонкий C ABI. Фреймворк не зависит от Node-API и несовместим с Node.js и Deno - он по построению роден экосистеме Bun.

## 2. Цели

- **Безопасность на границе FFI** - граница там, где заканчиваются гарантии Rust; фреймворк ставит на её место явные правила.
- **Ясное владение** - у каждого значения, пересекающего границу, есть одна отвечающая за него сторона, и это выражено в типах.
- **Удобство разработки** - аннотируй, собирай, импортируй типизированные функции; ошибки - это диагностика, а не загадки.
- **Долгосрочная сопровождаемость** - небольшие крейты, построение снизу вверх; детерминированные артефакты, которые можно коммитить и смотреть в diff.
- **Bun прежде всего** - без компромиссов ради других рантаймов.

## 3. Обзор архитектуры

Три плоскости, соединённые одним контрактом:

```mermaid
flowchart LR
    R["Rust-стек<br/>(14 небольших крейтов, фасад сверху)"]
    A["тонкий C ABI<br/>(единая форма: статус + выходной параметр)"]
    J["JS-интеграция<br/>(пайплайн, лоадер, CLI)"]

    R --> A --> J
```

**Rust-сторона, снизу вверх.** Опубликованный крейт `bffi` содержит весь стек в виде модулей под feature-гейтами с сохранением домёрженных имён (`bffi::bffi_core`, `bffi::bffi_types`, ...): `bffi-core` - фундамент (дескрипторы с поколениями, реестр объектов, политика границы); выше - `bffi-error` (отображение `BffiError` -> JS Error), `bffi-types` (преобразования, SIMD UTF-8, общий wire-кодек), `bffi-object` (ObjectWrap), `bffi-callback` (двусторонние колбэки и универсальный callback ABI), `bffi-event-loop` (очередь и способы опустошения), `bffi-async` (фьючерсы Rust как JS Promises), `bffi-dts` (IR дескрипторов и генераторы), `bffi-build` (экспорты рантайм-ABI и loader JSON). Отдельный крейт проц-макросов `bffi-macros` (физически неизбежно: проц-макрос не может жить внутри обычного крейта) предоставляет `#[bffi]`, `#[bffi_async]` и макросы классов, делясь внутренностями через модули `support`/`class`. Фасад реэкспортирует всё плоско, плюс пространства имён `core`/`types`/`dts`/`object`/`build`/`r#async`, которые раскрытия макросов называют по умолчанию. `bffi-native` - эталонная cdylib.

**JS-сторона.** `@z2net/bffi` (packages/bffi) - конфигурируемый пайплайн (cargo build, loader JSON, сгенерированный TypeScript, dlopen) плюс типизированный лоадер времени выполнения. `@z2net/bffi-cli` (packages/bffi-cli) - CLI `bffi`: init, build, check, doctor, codegen, pack, fetch. `@z2net/bffi-native` (packages/native) - опубликованное семейство эталонных нативных модулей.

**Как путешествует экспорт.** Каждая аннотированная сущность даёт на этапе компиляции две вещи: тонкую C-функцию-обёртку единой формы (статус плюс выходной параметр) и дескриптор. Дескрипторы агрегируются в одно определение модуля на крейт; эта агрегация - полная машиночитаемая правда об экспортах. Схема полна, поэтому JS-сторона управляет всем обобщённо - поиск символов, передача аргументов, декодирование результатов и ошибок - без единой рукописной привязки.

## 4. Модель безопасности

Это инварианты, а не детали реализации:

| Инвариант | Обоснование |
| --- | --- |
| Копирование по умолчанию на границе. | Никаких разделяемых времён жизни двух языков, если явно не попросили. |
| Zero-copy только через `bffi::unsafe_zero_copy`. | Опасная возможность должна быть видна в месте вызова и никогда не подразумеваться. |
| Дескрипторы с поколениями + теги типов. | Устаревший или чужого типа дескриптор никогда не попадёт в переиспользованный слот или не в тот тип. |
| Каждое тело `extern "C"` живёт по политике границы: без обёртки в debug (так проще отлаживать), под `catch_unwind` в release. | Артефакт - cdylib, загруженная **внутрь** процесса Bun; аварийное завершение убивает хост. Паники становятся JS-ошибками в продакшне и никогда не пересекают границу как неопределённое поведение. |
| UTF-8 - каноничная кодировка границы. | Один строковый контракт; cstrings `bun:ffi` остаются корректными. |
| Публичный Rust API - 100% safe. | `unsafe` живёт только внутри крейтов, за проверенными дверями. |
| Ошибки - значения: `BffiError` = код + сообщение + источник; доменные ошибки конвертируются без потерь. | JS-сторона превращает их в `Error` с `cause` - сбои структурированы и никогда не молчат. |
| Стабильные E-коды диагностики макросов. | Макросы должны падать читаемыми, grep-аемыми ошибками, а не кашей из токенов. |

## 5. Модель асинхронности и event loop

JavaScript исполняется ровно на одном потоке. Вокруг него сотрудничают три роли:

- **JS-поток** - единственный поток, исполняющий JavaScript; он же опустошает event loop.
- **Потоки-исполнители** - опрашивают фьючерсы Rust; JavaScript они не касаются.
- **Поток таймеров** - обслуживает дедлайны (sleep, таймауты); JavaScript он тоже не касается.

Разрешение задач и вызовы колбэков, возникшие вне JS-потока, **доставляются, а не исполняются**: они ставятся в очередь и выполняются на JS-потоке во время опустошения. Вызов не из того потока отклоняется (или маршалится через очередь), но никогда тайно не проталкивается в JavaScript.

Опустошение - **явный контракт**: встраивающий код вызывает pump (или запускает цикл) когда считает нужным - обычно по задокументированному периодическому шаблону. Фреймворк никогда не ставит скрытые таймеры и не вызывает pump неявно. Отмена кооперативна - отменённая задача уничтожается на ближайшей точке опроса - а таймауты являются полноценными комбинаторами. Tokio - опциональный выбор исполнителя, не требование.

## 6. Модель TypeScript и кодогенерации

**Дескрипторы - единственный источник истины.** Одна агрегация на крейт превращается в каноничный детерминированный loader JSON (схема v1), из которого детерминированный генератор производит типизированный TypeScript-модуль с точными типами. Сгенерированные файлы байт-стабильны: их можно коммитить и спокойно смотреть в diff.

Рукописных привязок нет. Если дескрипторы и сгенерированные файлы расходятся, `bffi check` падает - расхождение это ошибка сборки, а не сюрприз времени выполнения.

## 7. Модель дистрибуции

Дистрибуция - **платформенные npm-пакеты**, в стиле napi-rs:

- Базовый пакет объявляет по одной записи в `optionalDependencies` на платформу, **закреплённой точно**; npm/bun ставит только запись, совпадающую с хостом.
- Каждый артефакт следует одному соглашению об именовании, а `resolvePlatformBinary` отображает платформа -> пакет -> путь к бинарнику. `bffi pack` собирает платформенный пакет из собранной cdylib.
- Платформенные пакеты публикуются **раньше** (или вместе с) базового пакета; неполная матрица видна при установке, а не обнаруживается в рантайме.

Поддерживаемые цели - семь 64-битных троек: `win32-x64-msvc`, `linux-x64-gnu`, `linux-x64-musl`, `linux-arm64-gnu`, `linux-arm64-musl`, `darwin-x64`, `darwin-aarch64`. 32-битных целей нет.

## 8. Примеры как исполняемые спецификации

Примеры-модули живут в отдельном репозитории,
[bffi-examples](https://github.com/z2net/bffi-examples); каждый из них - самостоятельный крейт и одновременно end-to-end тест одного среза дизайна:

- [sqlite](https://github.com/z2net/bffi-examples/tree/main/sqlite) - полный пайплайн на реальной нагрузке.
- [async](https://github.com/z2net/bffi-examples/tree/main/async) - фьючерсы как Promises, отмена, таймауты, явный pump.
- [event-loop](https://github.com/z2net/bffi-examples/tree/main/event-loop) - очередь, опустошение, маршалинг.
- [callbacks](https://github.com/z2net/bffi-examples/tree/main/callbacks) - оба направления, гейт JS-потока, доставка через маршалинг.
- [records](https://github.com/z2net/bffi-examples/tree/main/records) - матрица композитов: рекорды, энумы, последовательности, поля и возвраты `Option`.
- [streams](https://github.com/z2net/bffi-examples/tree/main/streams) - pull- и push-продюсеры, обратное давление, элементы `Result`, доставка по wake.
- [errors](https://github.com/z2net/bffi-examples/tree/main/errors) - `#[derive(BffiError)]`: пользовательские коды, `e.name` / `e.payload`.
- [wry](https://github.com/z2net/bffi-examples/tree/main/wry) - окно веб-вью под управлением Bun (референс по привязке GUI; см. [docs/BINDING-GUI.md](https://github.com/z2net/bffi-rs/blob/main/docs/BINDING-GUI.md)).

## 9. Журнал решений

Принятые решения, по одной строке:

| Тема | Решение |
| --- | --- |
| Совместимость | Только Bun; без слоёв Node.js / Deno. |
| Буферы | Копирование по умолчанию; zero-copy только через `bffi::unsafe_zero_copy`. |
| Дескрипторы | Индекс с поколением + тег типа (`u64`). |
| Паники | В release конвертируются в JS `Error`; abort допустим только в debug. |
| Строки на границе | Каноничный UTF-8. |
| C ABI | Единая форма: статус + выходной параметр, для каждого экспорта. |
| Event loop | Явный контракт pump/run; доставки исполняются на JS-потоке. |
| TypeScript | Дескрипторы - единственный источник истины; детерминированная генерация; схема v1. |
| Дистрибуция | Платформенные npm-пакеты вместо монолитного бинарника; точные пины. |
| Инструментарий | Bun >= 1.4.2 (проверяется); Rust 1.98.0 (закреплён). |
| Цели | Только 64 бита (семь троек); 32 бит - пока нет. |
| Диагностика | Стабильные E-коды ошибок макросов. |
| Лицензия | MIT. |

## 10. Не-цели

- Совместимость с Node.js или Deno.
- Совместимость API с `napi-rs`.
- Прятать границу FFI за магией - граница остаётся читаемой и явной.
- Zero-copy по умолчанию.
- 32-битные цели (пока).
- Максимальная производительность любой ценой на старте.
